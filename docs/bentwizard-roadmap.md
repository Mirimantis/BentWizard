# BentWizard — Timber Framing Workbench Roadmap (rev 4)

**Name:** BentWizard (retained from the prior iteration; architecture is new)

**Target platform:** FreeCAD 1.1.1
**Pilot project:** Generic test bent

Rev 4 (September 2026) is written against proven behaviour: spike rounds 1–3 and the datum-accessor session (`docs/session-frame-accessors.md`, Parts A–H) replaced rev 3's mechanism — faces 1–4 with parity tables, joints rebuilt sketch-by-sketch into the timber, typed stick lengths reconciled by `Stick_Allowance_*` and a companion VarSet, a handed-template flag — with the one described in `docs/bentwizard-workflow-rev2.md` and built in September 2026. Sections rev 3 carried for that mechanism (Layout rules, Parametric layout, frames-at-face, mate parity) are gone; what they protected is restated below.

## Governing Rules

**Tier 1 — Geometry stays native. Unchanged, non-negotiable.**
All solid geometry is built from ordinary FreeCAD objects: Sketches, Part Design features, LCS datums, Booleans, Assembly joints. Anything the workbench produces must be editable by hand with stock FreeCAD, as if a person had modeled it. This is the lesson of the failed prior attempt.

**Tier 2 — Non-geometric data degrades gracefully.**
Species, grade, joint metadata, pairing, component roles, check results and similar data live in custom properties on native objects: visible and editable without the workbench, surviving round trips. Workbench-gated *functionality* is acceptable; gated geometry is not.

**Prefer native mechanisms over reimplementation.** Instancing is `copyObject`, not a rebuild engine. Placement is an expression, not computed geometry. Both prior failures violated this, in different ways.

**The timber is the design solid; joinery is a cutter and/or an adder.** `LengthZ` is the frame dimension, bearing face to bearing face, and does not change when joinery is applied or swapped. A joint template half carries a `Cutter` (modelled in −Z, applied with a `Cut`) and/or an `Adder` (modelled in +Z, `Fuse`). Order length is measured off the finished solid (`measure.py`: long point for an angled end), never typed. **No layout doctrine**: square rule versus mill rule is shop practice; the deliverable is accurate geometry and good dimensioned drawings, and housings remain a joint parameter because they are real geometry.

**One solid is the assertion.** Round 3 found three distinct failures — a 1 mm gap in a fusion, a cutter spanning the whole section, an operand seated in the wrong frame — that each produced *exactly* the expected volume, passed `isValid()` and `isClosed()`, and left every object Up-to-date. Only `len(Solids) == 1` told a joint from a severed timber. Apply refuses on it, the audit reports it, the registration sweep hunts for it.

## Phase 0 — Manual Workflow Definition (complete, superseded)

The twelve manual sessions of 2026 (`phase0/`, `docs/bentwizard-phase0-workflow.md`, findings #1–#15) proved the conventions rev 1 was built on and produced the friction findings still cited here. Their mechanism is retired; the findings stand.

## Phase 1 — Joint Library & Application Tool (rebuilt September 2026)

- **Timbers** (`timber.py`): a Body with a nested `TDim_` VarSet (`WidthX`, `WidthY`, `LengthZ`, `PositionTag`), a section centred on the axis (half-width constraints from the origin, never Symmetric — finding #13), a stick pad, and both **end datums** from birth. Dimensions take literals or expressions on project VarSets (the ƒx fields).
- **Datums** (`datums.py`, `facetable.py`): the LCS a timber carries for its joinery — placed directly from the four-row face table (position from the section, rotation a literal, `Station` driving `Placement.z`), never by attachment (three axis bugs) and never by hand (two GUI failures). One rule on every row: local Z out of the material, local Y along the timber toward end A, X = Y × Z — so components are portable between faces with no parity correction. Accessors `WidthU/WidthV/DepthW` bind to the timber's own Dims; pairing is two strings, `MateDatum` and `Joint`, because a link cannot cross a Body boundary and two datums reading each other is an object-granular dependency cycle. The cross-timber accessors (`HostWidthU … MateDepthW`) therefore live on the **joint VarSet**. **Add Datum** is the layout-first command; Apply also places datums on demand.
- **Templates** (`template.py`, `library/`): two timbers with a paired datum each, one joint VarSet `J-<Kind>-000` (parameters, tooltips, optional `<Name>Min/Max` ranges), component bodies with `ComponentRole`/`ComponentOrder` placed on the datums and applied by Booleans. A component reads only its own datum and the joint VarSet (strict lint). Shipped: `Joint_Butt` (the jointless starter, and a real bracketed-connection joint) and `Joint_HousedMT`, both script-built by `scripts/build_library.py`.
- **Apply Timber Joint** (`apply.py`): copy the VarSet and component bodies out of the template (`copyObject(objs, False)`, the VarSet in the set so its references remap; a cross-document copy leaves unresolved references in a bare `Label.Prop` form, matched too), relabel, pair the datums, re-point the datum tokens, **mirror on parity** (below), Boolean in declared order, assert one solid, write the handle, and — with *Assemble now* — pre-position the free timber and seat it. **Remove Timber Joint** deletes the Booleans, mirrorings, components, handle, Fixed joint and VarSet and unpairs the datums, which stay.
- **Parity and the mirror rule** (Part H2/H3, generalised): any rigid Z→−Z flip preserves exactly one in-plane axis and swaps the other, so "the same timber-local offsets at both ends" is a mirror, not a rotation. Each face and end carries a parity (`EndB`, `XPos`, `YPos` +; `EndA`, `XNeg`, `YNeg` −); a component is mirrored across its local X (`Part::Mirroring`, carrying the Placement) when the target datum's parity differs from the authoring datum's. The −X face equals the +X face reflected through the timber's YZ plane composed with that mirror, so the one rule covers ends and opposite faces — pinned on all four faces and both ends by `test_apply.test_parity_keeps_timber_local_offsets`. ~~No template flag, no dialog option; symmetric components mirror to themselves.~~ **Partly reversed 2026-09-19 (Adam):** the mirror is correct but not free — a `Part::Mirroring` claimed by the timber's Boolean links a component body at the document root, which the GUI reports as an out-of-scope link on every recompute (14 warnings per `Bay` edit on a 3-bent frame), and it leaves a loose source body in the tree for every mirrored component. Principle adopted: pay once when a template is authored, not on every application, edit and recompute. Step 1 (built): a template declares `Handed`; `Handed = False` is never mirrored, and the template bar checks it is symmetric. Step 2 (pending, with the dovetail): a handed template carries both hands, and Apply picks the one matching the datum's parity — no mirroring at all. An `App::Link` with `ScaleVector (-1, 1, 1)` was tested as a drop-in replacement (identical geometry on all eight face/end cases, zero scope warnings) and kept as the fallback; it still leaves the loose source body.
- **Flat frame — adopted 2026-09-19 (Adam), replacing the two-level design below; built 2026-09-23** (workstreams A, C and D; B retired, since 26.3's fine-grained recomputes do its job; E, export to Assembly, is Phase 2 — `docs/rebuild-flat-frame-handoff.md`). **As built there is no Assembly object at all** — see "No Assembly object at all" below; the opening sentences record the design as first adopted. A frame is exactly **one** `Assembly::AssemblyObject`; every timber is a direct member. Bents, bays and any other groupings are `App::DocumentObjectGroup`s (Std Groups) inside it — tree organisation only, invisible to the solver. No assembly ever moves, so FreeCAD's Fixed-joint markers (drawn at twice a moved sub-assembly's shift — its own bug, same class as upstream #17398/#31083) and its drag and joint tools stay correct. **Timbers are seated by expression, not by the solver** (spike round 2, `docs/spike-flat-frame-results.md`): the timber joint that first connects a timber (its *placing joint*) carries a `Seat_J-…` VarSet, nested under its handle, computing `host · flip · mate⁻¹` from the two datums; the timber's `Placement` reads it. Placing joints form a spanning tree from a grounded timber; a joint whose timbers are already placed (the second tie of a bay) places nothing and Audit Timbers' misfit check verifies it closes. A `Bay` edit is a plain recompute — exact and warning-free to 20 bents, where the solver failed at 5 (closed loops of Fixed joints) and could not re-space 10 even loop-free. Rule 3 ("placement is an expression") now covers the frame. **The placement tree is not the load path:** the structural graph (Phase 4) is derived from all timber joints plus roles, bearing faces and supports. Refinement for later: Apply prefers the supporting side as the anchor (beam from post, post from sill) so placement mostly follows gravity — a convenience, never a structural input. **No Assembly object at all** (Adam, 2026-09-19): with seats placing every timber, the assembly's only remaining job was grounding the principal timber for a solver that no longer runs — and a grounded joint does not lock anything without it. The frame is a **Std Group**; the principal timber is anchored by binding its `Placement` to a `FrameOrigin` placement on the project variables (an expression-driven value cannot be dragged or typed over, and moving the whole frame becomes one edit). This retires most of `assemble.py`, Assemble Timbers, and Duplicate Timbers' assembly step, and re-files the handles under the frame group. **Export to Assembly** — convert a finished frame into a FreeCAD Assembly with Fixed joints — becomes an output feature (see Outputs). Dragging is not wanted: a timber is positioned by its joints and its variables, never by hand (the sketch item above is the visual way to edit those). **Recompute isolation is retired — the engine does it** (2026-09-20). FreeCAD 26.3's fine-grained recomputes track dependencies per *property*, including expression edges, and are on by default in the weekly. Measured: the **unsplit** five-bent frame recomputes 145 objects in 0.88 s against 215 / 1.51 s fully split, with a flat ladder between — so every level below would be cost without benefit, and layout variables can be grouped thematically the way a framer expects (`docs/spike-fine-grained-recompute-results.md`). **Confirmed at scale 2026-09-22** (findings 13–15 there): sharing a VarSet costs nothing — a `Bay` edit recomputes the identical objects shared or isolated, at 2, 5 and 10 bents — and the cost is linear, ~36 objects and ~0.23 s per bay on the 7010 (325 objects / 2.15 s at ten bents). The catch: 26.3 also resolves a `PartDesign::Boolean`'s operand globally (upstream #30393 → #30575), which the component mechanism depends on; Adam's decision is to hold the old frame behind `UseLegacyBodyPlacement` and work toward global binding and full 26.3 compatibility by release (`docs/freecad-26-3-compatibility-brief.md`). 26.3 is now the minimum (2026-09-21), so the costs below are history — they describe 1.1.3's engine. **What the splits would have been** (spike round 4): FreeCAD's dependency graph is per *object*, so a `Bay` edit recomputed 514 of 1676 objects (4.6 s at five bents) — nearly all of it posts whose cuts had not changed. Splitting the objects along what actually varies takes it to 215 objects / 1.46 s (3.2x), after which *no post geometry recomputes at all* — only the ties that changed length and their tenons. What must be split: each project variable (a variable shared with others cascades to all their readers), `LengthZ` away from the section (`TLen_<timber>` beside `TDim_<timber>`), the joint VarSet down to parameters only with per-side `Plc_` (datum placement) and `Sec_` (section, read from the Dims VarSet, never through the datum), and **`DepthW` away from `WidthU/WidthV`** — at an end datum `DepthW` *is* the length, and that one split is most of the win. Costs: up to six accessor objects per joint instead of one (only those a component actually reads — three for `Joint_HousedMT`), two per timber, and Apply's wiring, the linter's component rules, the template bar and `datums.host_datum`'s pairing lookup all move with the accessors; the host/mate role becomes an explicit record instead of something inferred from the `HostWidthU` expression. Templates keep the single-VarSet form and Apply expands it. Accepted by Adam 2026-09-19. ~~**A central "master variables" VarSet that the isolated ones read would undo all of it** (measured): the edited object must be the isolated one, so the single place to edit everything is the panel, not an object in the model.~~ **Overturned on 26.3** (2026-09-22, finding 15): the same probe no longer cascades — editing `Central.Bay` leaves a reader of `Central.Span` untouched. One central place for the framer's variables is safe; whether the panel is still the better place to *find* one is now a front-end design choice, not an engine constraint.
- **Two-level structure assembly — superseded by the flat frame above** (`assemble.py`, unchanged in shape from July 2026): bents are nested `Assembly::AssemblyObject`s inside a parent frame; deterministic container rules (both loose → new bent grounded at the host timber; one loose → joins the other's; different assemblies → deepest common parent, the first cross-bent joint creating the frame grounded by the oldest bent); one red padlock per assembly level; Apply assimilates each joint as it is made, **Assemble Timbers** is the bulk/repair/reground path. What changed: every seat is antiparallel now, so the Fixed joint's `Offset1` is a constant 180° about local Y, and the mover is **pre-positioned at its exact seat before the first recompute with the joint present** — MbD otherwise rotated the *grounded* post (Step 0 probe, ~20° on the ±X faces). Headless, a parameter edit leaves the assembly `Touched` until `solve()`; the GUI is expected to re-solve on recompute (to confirm).
- **Per-joint handle** (`joint_handle.py`, `view_joint_handle.py`): as before — an `App::FeaturePython` holding the joint VarSet, linked to it and to the host datum (structural, never label-matched), filed in `TimberJoints_<Assembly>` inside the joint's assembly, marked in 3D by a transient ViewProvider, whole-joint operations on its tree context menu (Joint parameters, Select joint members, Remove timber joint). Interaction is tree-side by platform limitation (FreeCAD #14701/#11429/#12826).
- **Duplicate Timbers** (`duplicate.py`): rebuild the timbers (Dims values and expressions carried; bindings naming the source itself copied as literals — finding #2), place their face datums again (station literal or expression), re-apply each fully-inside joint from its `TemplateSource` with its current parameter state, reproduce relative placements, and optionally assemble the copies into a new offset bent.
- **Show Face & End Marks**: ±X/±Y and A/B on every timber, a scene graph on the Body's view provider, nothing in the document.
- **Audit Timbers** (`measure.py`): per timber the design and order length, how far joinery reaches past each end, the solid count, and every datum's placement and pairing — the report a framer reads before ordering.
- **New Joint Template / Save as Joint Template** (`template_library.py`, `template_check.py`): a starter is any template with no Boolean in it; saving relabels to the kind and reports the **template bar** — the linter, the skeleton rules (two timbers, one VarSet, a pairing under it, every component declared, placed on a paired datum and applied by a matching Boolean), the stem contract, a real `TemplateSpec` load, and the FreeCAD half: one solid per timber, growth direction, and a sweep of every numeric parameter across its declared range (or 25–150 % of its default) recording where a timber stops being one solid, persisted on the VarSet as `SweepFindings` for the apply dialog to warn from. **Warn twice, block never.**
- **Linter** (`linter.py`, rev 2 §6): strict — solid-face references, reserved label characters, LCS child-plane attachment, datums not placed by attachment, datum declaration matching its face-table row, no link properties on datums, pairings that resolve both ways, component declaration, component reference scope, one operand per Boolean and never an `App::Part`. Advisory — naming, UpperCamelCase properties, duplicate labels, Symmetric constraints, group-binding deviation, stale attachment offsets, auto labels, duplicate and missing tooltips, cutters after adders.

### Layout: project variables drive stations and lengths

The grid is authored on project VarSets; datums and Dims bind to it. A datum's `Station` bound to `<<ProjectVars>>.GirtLine` moves a whole line of joints at once; a beam's `LengthZ` bound to a bay's clear span moves the far post. With the design solid bearing-to-bearing there is no allowance arithmetic and no dependency cycle — the rev-3 companion VarSet, `Span_Basis`, `Stick_Allowance_OC/FTF` and Drive Length from Layout Distance are all gone. What remains owed is convenience: a **beam tool** that writes `LengthZ = <span> − half sections` (an expression, not a number) for an infill timber between two datums, and a **New Project** dialog that seeds the project VarSet with real starting variables.

### Deferred, in rough order

- **Per-timber face labels**: a `Role` on the Dims VarSet defaulting `FaceLabelXPos …` (post → outside/inside/bent-left/bent-right; plate → top/bottom/outside/inside), user-overridable, surfaced on drawings and in the face pickers. Never a selector — renaming a face must never affect geometry. The pickers show ±X/±Y until then.
- **Created-part roles**: a component with no target timber — the wedge in a tusk tenon, a peg — cloned as a standalone solid, assembled to the datum, routed to the hardware schedule rather than the cut list.
- **The dovetail rebuilt** on the new contract (a chiral-looking joint that mirrors correctly is the test the parity rule wants). It is the first handed template, so it brings step 2 of the handedness decision with it: both hands carried in the template, Apply choosing by parity, the template bar checking the two hands are true mirror images. Open: whether Save as Joint Template generates the second hand for the author to adjust, or the author models both.
- **Beam tool**, stage 1 (dialog: two datums, one template both ends, `LengthZ` as an expression) then stage 2 (the 3-click gesture, which wants parametrically angled joints).
- **Parametrically angled joints**: a joint angle as a VarSet property driving a datum's rotation, bounded by a declared range; the datum table gains an angle term.
- **A mirrored component's source body** sits at the document root beside its mirroring (the Boolean claims the mirroring, not the source). Adam objected (2026-09-19): it clutters the tree, and the mirroring's link to it is out of scope. Now limited to handed templates (`Handed` flag); goes away entirely with both-hands templates (see the dovetail item).
- **Archetypes** (Adam, 2026-09-18). New Timber gets an option to make the timber an *archetype*: its parameters go on a VarSet the timber references, filed in a `TArchetypes` group at the document root, named at creation. Later timbers pick an archetype and reference the same VarSet, so editing the archetype updates every timber built from it; a tool makes an archetype from an existing timber. The same for timber joints: `JArchetypes`, a joint VarSet as the type layer a joint instance binds to (this is the "parameter presets" open item, given a home).
- **Re-place operations** on the handle's context menu (move a joint to another datum without removing it): a token substitution over the component's expressions plus a re-pair — the mechanism is the one Apply already runs.
- Cross-joint interference checking, dihedral angle finder, raising calculations — unchanged from rev 3, see Phase 4.

## Phase 2 — Cut Lists & Drawing Automation
- Cut list is a **procurement document**: timber ID, species, grade, moisture, finish, cut type (boxed heart / FOHC / quartersawn), section, **design length** (`LengthZ`), **order length** (`measure.order_length`, the long point, plus the trim-allowance parameter), board feet per stick, and order totals. Joinery callouts live on shop drawings / a joinery schedule, not the cut list.
- Specification fields (species, grade, moisture, finish, cut type) are Tier 2 properties on each timber; the generator reads them — the spreadsheet is output, never the source of truth.
- Hardware/peg schedule: generator sums per-joint counts (VarSet properties like `PegCount`) grouped by diameter.
- Batch TechDraw: projection-group-based dimensioned shop sheets per FabricationSignature (quantity + MemberID list on each; per-timber sheets as an option); frame/bent elevations. Generated sheets set dimension/font styles explicitly, never inheriting user preferences. Round 3 T6d: views and dimensions survive a parameter change over a fused tenon with no `hasher mismatch` warnings.
- **Positional IDs are display data**: the permanent identity is the serial Label (`T-Post-003`); position lives in `PositionTag`, which drawings and lists print; renumbering a position never touches a label, an expression, or geometry.
- **FabricationSignature**: normalized hash of species, grade, section, order length, end cut angles, and joint layout in timber-local coordinates. Identical signatures form fabrication groups. A mirrored component hashes differently.
- Shop drawings carry face labels and A/B end labels per the adopted face vocabulary; face labelling/order is configurable (a competing SketchUp plugin added an option purely to mimic Dietrich's face order — drawing conventions are muscle memory). Reference marks, where a shop wants them, follow the crow's-foot convention (drawn at *half* the edge's width, so they cannot be mistaken for a carpenter's triangle).
- **Shop-drawing generation is the fragile last mile**: the highest density of complaint about existing timber software is the drawing/BOM output, not modeling. Treat this phase as the one that decides whether the workbench is genuinely useful.
- **Degree of Difficulty per timber** (Tier 2): a joinery-complexity tag feeding labor estimating.
- **Share-with-viewers workflow**: FreeCAD already exports formats free 3D viewers open; verify and document one route rather than building anything.
- **Export to Assembly** (Adam, 2026-09-19): a frame carries no Assembly object of its own (see *Flat frame*), so converting one into a native `Assembly::AssemblyObject` with a Fixed joint per timber joint — grounded at the principal timber, the seats becoming the solver's starting pose — is an **output**, for anyone who wants to drag, explode or animate the frame in FreeCAD's own Assembly workbench. One-way: the exported assembly is a deliverable, not a second source of truth.

## Phase 3 — Species & Grade Material Library
- Custom properties / Materials cards with NDS design values (Fb, Ft, Fv, Fc, Fc⊥, E, Emin), green vs. dry. Tier 2 compliant.
- **Reference data system**: bundled read-only CSVs (species_properties from NDS, section_properties) with a user-override directory checked first at lookup; user rows visually distinct, base rows never edited in place. The New Project dialog's standard-section list reuses it.

## Phase 4 — Structural Checks (start simple, grow later)
1. **Load-path continuity** — every timber has a complete path to a bearing point; disconnected members flagged.
2. Span-table checks (AWC tables via the reference data system) and rule-of-thumb checks, advisory only.
3. Member stress checks driven by tributary-area load accumulation from **BuildingParameters** (roof material / snow / occupancy / wind presets, ASCE-derived, a project-level parameter group).
4. FEM studies of individual joints (orthotropic properties via CalculiX) seeding a joint_capacities table.
5. Lightweight frame analysis with beam elements and semi-rigid joints; racking checks; bearing-point reaction schedule.
6. Load/capacity color overlay via native body ShapeColor; structural report with clickable findings.
Always labeled design guidance, not stamped engineering.

**Cross-joint interference checking**: two different joints colliding inside one timber — a tie's tenon and a brace's tenon meeting in a post. Each joint's components are known per timber (`joint_components`), so bounding volumes in timber-local coordinates can be compared, with a true intersection only for candidates that overlap.

**Raising calculations — weights, tipping and balance points**: per-timber and per-assembly weight, centre of mass, and the tipping/balance points a crew needs to rig a raise (the Guild's own literature computes these by hand). Depends on Phase 3; ships with the design-guidance framing and shows its assumptions.

## Phase 5 — Building Composition (future, preserved from prior iteration)
Ground planes and bearing-point projection; auto-generated sill beams; split-level ground planes; frame openings generating headers/trimmers with load redistribution; wall-opening placeholders; chimney clearance zones; cantilever load paths; bent layout templates (King Post, Queen Post, Hammer Beam) as saved native layouts.

## Framer-facing front end (adopted August 2026)

**Who it is for**: individual DIY builders through small independent contractors — the people priced out of SketchUp subscriptions and nowhere near Dietrich's or Cadwork. Free and open-source, genuinely useful rather than a demo: a tool for designing frames, producing shop drawings and BOMs, and preparing for a build. Not aimed at non-technical clients driving it themselves: a few hours of learning is an acceptable price, weeks is not. Sharing with people who need no edit access goes through FreeCAD's export.

External research supports the shape: purpose-built timber software earns adoption by being domain-native, and the realistic win condition for trades software is "good enough that a junior person can drive it for the senior framer" — legibility of *output* over hand-holding of *input*.

**Delivery: a dock panel, with the tree left available.** A full workspace that hides FreeCAD's UI is deferred.

**Scale target**: multi-story, multi-wing structures up to ~12 bents; prove features at a two-story house and a standard barn first.

**Sequencing is a priority, not a rule**: front-end features ship as soon as they are thought through and have a back end. Both GUI failures of the July–August work were affordance problems, not logic problems.

### Near-term
- **Variable → highlight everything that reads it** (transitive closure over `InList`/`OutList`; a transient view override, never `ShapeColor`).
- **Toolbar icons**, so commands can group into dropdowns.
- **Bulk-apply a project variable to selected members** — bind every selected datum's `Station` (or every selected timber's `LengthZ`) to one variable.
- **Face labels per timber role** (above) feeding the face pickers and the marks.

### Next (in Adam's priority order)
1. **3D selection → a panel showing parameters, state and relationships** — a timber's Dims and datums, a joint's parameters, what drives what, and the tools that act on it. A 3D right-click context menu is not possible (upstream); the panel is the workaround. **Trace to the source** (Adam, 2026-09-19): values reach a timber through a chain of VarSets — Dims ← project variables, joint parameters ← archetype, a seat ← two datums — and "where does this number actually live?" is already hard to answer with four VarSets, let alone a real frame. The panel must follow an expression to its **ultimate source** and offer that for editing in place, however deep in the tree it sits, rather than sending the framer hunting. Nothing about this is timber-specific, so it may be better as a **companion addon** (a general FreeCAD expression-dependency browser/editor) that BentWizard's panel uses when present — decide when the panel is built; the tracing itself is `ExpressionEngine` walking, which `linter.Model` already does structurally.
2. **Generate a bent from a 2D sketch — one way only**: the sketch is a starting surface, not a permanent source of truth. Trace over an imported image/PDF; a ground grid driven by project variables; **isolate a bent for orthographic editing** first, since it is most of what "work on one bent in 2D" means. *One-way means the timbers never write back: moving a timber does not re-dimension the sketch* (Adam, 2026-09-19). It does **not** mean the sketch is disposable — when the sketch's dimensions carry the same expressions that drive the timbers' stations and lengths (`<<ProjectVars>>.Bay` and the rest), the sketch becomes the drawing that shows **which variable is which dimension**, edited from either side because both read the same variable. That is the visual, intuitive form of parameter editing; it plugs into seats-by-expression unchanged, since a station or a length is a station or a length wherever it is edited.
3. **New Project dialog**: framing conventions, species/grade/moisture, the standard sections this shop buys, trim allowance, peg stock, starting layout distances — skippable, everything editable afterwards. Workbench preferences hold the user's defaults; project settings are Tier-2 properties on a `Project_` VarSet seeded from them. It creates the project VarSet with real starting variables, which is what makes binding a station or a length to the grid a pick rather than a hand-authored expression.

### Later / bigger
- Dimension displays in the 3D view, including which variable feeds each (custom-drawn, view-only; prototype one type first).
- Joint library previews (a screenshot at save time is easy; an embedded viewport is later).
- A workspace that hides FreeCAD's UI, only if the dock panel proves insufficient.
- **Spin the naming prompt off** (Adam, 2026-09-18): the dev helper that prompts for a label when a VarSet, Body or other object is created (`devBuildMacros/EnforceNaming.FCMacro`, installed as `Mod/EnforceNaming`) is liked, but it carries BentWizard naming language into every workbench. Make it a separate lightweight plugin that only asks for a name, with no guidance about what the name should be.

### Principles
- **Do not be prescriptive.** Provide multiple routes between stages and smooth transitions back and forth.
- **Let the user pick which parameter they author** — "choose the driver, the others derive" as a repeatable idiom, since a property is either a literal or expression-bound.
- **Terminology stays governing**: timber-framing terms everywhere, "timber joint" never bare "joint", *datum* never "frame" for the LCS, units deferring to the user's FreeCAD schema.
- **Name things after the work, not the implementation.**

### Ergonomic debt paid and remaining
Rev 3's named debt — the two-VarSet juggle (`Tenon_Length` living on a companion the joint consumed from) — is gone with the companion. **Paid 2026-09-21:** the joint VarSet's tool-written accessors (`HostWidthU …`) no longer sit beside the framer's parameters — they moved to an `Accessors_<joint>` VarSet under the handle, so the joint VarSet a framer opens holds only what they edit. Remaining: the apply dialog's role rows now say *Primary — passing* / *Secondary — butting* (host / mate, passing or butting read from where the template put each datum) with the template's own timber name in the tooltip; an explicit per-template role name with a load direction is still the open item below.

## Open Items
- **Dihedral angle finder**: pick two connected faces, get the angle between them — lands with parametrically angled joints.
- **Principal Post visibility**: distinguish the grounded timber in 3D and the tree beyond the stock padlock; a picker in Apply's dialog when both timbers are loose.
