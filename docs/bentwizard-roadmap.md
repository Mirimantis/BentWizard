# BentWizard — Timber Framing Workbench Roadmap (rev 3)

**Name:** BentWizard (retained from the prior iteration; architecture is new)

**Target platform:** FreeCAD 1.1.1
**Layout convention:** Mill Rule — drawings dimension an idealized straight, square timber (reframed July 2026; see Layout rules section. Square Rule remains supported: its reduce-to-ideal step is field work, not model content)
**Pilot project:** Generic test bent

## Governing Rules (amended)

**Tier 1 — Geometry stays native. Unchanged, non-negotiable.**
All solid geometry is built from ordinary FreeCAD objects: Sketches, Part Design features, datums, Assembly joints. Anything the workbench produces must be editable by hand with stock FreeCAD, as if a person had modeled it. This is the lesson of the failed prior attempt.

**Tier 2 — Non-geometric data degrades gracefully.**
Species, grade, joint metadata, check results, and similar data may be workbench-aware. Requirements: (a) with the workbench uninstalled, parts and assemblies remain fully editable — custom properties on native objects satisfy this, since FreeCAD stores them in the file and shows them in the property panel regardless; (b) custom data survives a round trip through a system without the workbench; (c) workbench-gated *functionality* (checks, reports, generators) is acceptable, since behavior — unlike geometry — is regenerable.

**Modeling convention — subtractive joinery.**
Joints are cut the way wood is cut: pockets and holes preferred over pads. Consequences:
- `Length` in a timber's VarSet = the full stick as purchased and cut, tenons and tongues included. Cut lists read it directly.
- Tenons via island pockets: one sketch with an outer removal loop and an inner tenon profile; the pocket leaves the island standing.
- Tenon shoulders land at `Z = TenonLength`, not the origin plane; assembly references use shoulder datums or expressions.

**Datum strategy (manual workflow):** sketch on native origin planes or faces with zero offset where possible; set depth by pocket/pad length, not datum offset; set position along the timber by sketch constraint. Reserve offset datums for genuinely floating planes and verify their resolved placement. (See findings log #10.)

## Phase 1 — Joint Library & Application Tool
- Joint templates as ordinary FreeCAD files.
- Apply-Joint tool: reproduces the manual steps — cloning native sketches/features, binding a shared VarSet — with parameters entered as plain numbers, expressions written programmatically.
- Mated-pair logic: one VarSet per joint instance drives both timbers.
- Reference-face aware: joint layout measures from the named reference faces and stick ends. Housings are **optional bearing features** (Mill Rule usage — spreading load across the full beam width instead of the tenon alone) with real designed depths.
- **Landing-face-relative joint definitions** (from findings #9): one joint instance = one VarSet + one landing-frame datum per timber role. Implementation verified in 1.1.1 (Phase 1 start): the frame is a `Part::LocalCoordinateSystem` datum; sketches and datums attach to the frame's own planes and follow it rigidly, so retargeting face/station/end/hand = re-placing one object. Caveat: followers must reference the LCS sub-element, not its child plane object (the latter resolves to identity placement). Template sketches are position-agnostic — constrained only to the joint VarSet and their own timber's Dims — and attach to the landing frame, which the tool places and orients (end, station, hand). Strict linter rules: one VarSet per instance; no multi-instance sketches; no cross-timber dims references; no solid-face references. Joint templates carry non-geometric schedule data as VarSet properties (e.g. PegCount).
- **New timber from template**: atomic duplicate of pristine template + VarSet with verified remap (findings #2, #12). **Duplicate Timbers** (née Duplicate Bent): instance-layer VarSets (Dims, joints) duplicate; group bindings preserved.
- **Two-level structure assembly** (adopted July 2026 after the first GUI shakedown; supersedes the brief bays-as-links design — links could not receive tie-beam joinery and weren't parametric, so every timber is a real body; FabricationSignature returns the deduplication at the Phase-2 list layer). Bents are nested `Assembly::AssemblyObject`s inside a parent frame assembly; assembly is not a second button — **Apply Timber Joint assimilates each joint the moment it's created** (`assimilate_joint`), with **Assemble Timbers** as the bulk/repair/reground path. Container rules, deterministic: both timbers loose → new bent sub-assembly grounded at the anchor timber (the Principal Post — framers measure everything from it); one loose → joins the other's assembly; same assembly → Fixed joint lives there; different assemblies → the joint goes to the deepest common parent, and the first cross-bent joint creates the frame, grounded by the *oldest* bent. Each timber joint = one Fixed assembly joint referencing the JointFrame/MateFrame LCS datums (never solid faces), reference form `(moving_part, ["Body.LCS.", ""])`. **Mate parity**: on faces where the landing frame's Z points into the wood (`FACES` flip_z — faces 2/3), plain frame coincidence seats the mate mirrored through the bearing plane (the shakedown's inverted end-B bent); the engaged pose is coincidence rotated 180° about the frame's local Y, carried in the Fixed joint's `Offset1` so its nominal pose IS the correct seat, and applied in `engagement_placement` (Preview shares it). Pinned by the face 1–4 × end A/B seating matrix (overlap ≈ 0). **No temporary anchors, ever**: grounds are each bent's internal principal timber and the principal bent in the frame — **one red padlock per assembly level**, meaning "the fixed reference *within this assembly*", not "grounded to the world"; only the chain frame → principal bent → Principal Post is world-fixed. Pre-seating moves the side **not yet connected to its assembly's ground** (`isPartConnected`, the new joint suppressed during the test) — a tie already seated on bent 1 stays put and the new bent comes to it. After a container seats, its internal assembly joints are touched (`refresh_joint_display`) so their icons follow — a joint's viewprovider doesn't redraw when only its container moved. An unconnected bent floats user-movable until a tie joint constrains it (verified: the parent solver leaves it untouched), then snaps to its parametric position — a plain recompute re-solves the chain, so tie-beam `Length` drives bay width live. (The Transform tool bypasses the solver by design; a transformed part snaps back on the next solve/recompute.) **Duplicate Timbers** reproduces relative placements and assembles the copies into a new offset bent sub-assembly, ready for tie beams (the 10-step bay sequence is a smoke test). Terminology guard: BentWizard joinery is a "timber joint" in all user-facing text; the `TimberJointVars` Std Group stays clear of every Assembly's own `Joints` group.
- **Per-joint 3D handle** (designed, next branch): a clickable marker at each timber joint for at-a-glance "this intersection is joined" and direct VarSet access — an `App::FeaturePython` with a Group extension holding the joint's VarSet, attached to the anchor's landing frame, ViewProvider (workbench-gated) drawing the marker. Degrades safely without the workbench: a proxy-less native object holding data, zero geometric effect. Apply Timber Joint creates it; a migration pass adopts existing joints; `TimberJointVars` then holds handles instead of bare VarSets.
- **Preview Mated Joint** (findings #7, #11): display both halves engaged for at-a-glance fit verification, independent of body placement.
- Generated sketches use centerline + half-width constraints, not Symmetry (findings #13).
- **Parameter sanity bounds** (inherited from prior iteration): apply-dialog computes min/max from the timbers involved — mortise width ≤ 75% of receiving extent, housing ≤ 50% of through-dimension, dovetail flare clamped to member extent. Linter: strict at severing limits, advisory warning at 35%.
- **User-authored joint templates**: a joint template is an ordinary FreeCAD file — one VarSet (the parameter schema) plus per-role feature stacks. Users author new joints by modeling them manually per project conventions; a "Save as joint template" tool validates (a linter built from the findings-log conventions: origin-plane sketches, single shared VarSet, no solid-face references, half-width constraints, naming, interior islands or removal regions) and registers the file into the library. The apply-joint dialog is generated from the template's VarSet properties — no per-joint code, so adding joints requires no programming. Clone architecture gives free versioning: template edits never affect already-applied joints.
- **Parameter provenance UI**: from any timber or joint, view where its numbers come from — group memberships, binding chains, and overrides; advisory linter reports group deviations.
- **Layered parameter groups**: instance VarSet properties may pass through by expression to group VarSets (type → section → project). Sharing = binding; overriding = replacing one property's expression with a literal; group membership = the binding itself (no hidden state, Tier 2 clean). Tools: "assign selected to group" (bulk expression rewrite), apply-dialog fields accept literal or group binding, advisory linter reports instances deviating from their group.
- **Handed template metadata** (adopted July 2026, testing notes): a Tier 2 `Handed` boolean on the joint template's VarSet. Fully symmetrical joints (defined from the centerline — which the centerline + half-width sketch convention already produces) set it false: Apply Timber Joint hides the hand option, and the linter skips hand-related checks. Phase 2's FabricationSignature already assumes this distinction exists ("handed mirrors hash differently") — making it explicit template metadata now feeds that directly. Same shape as the primary/secondary-roles open item: template self-describes, tools read it, no per-joint code.
- **N-part joint templates / created-part roles** (adopted July 2026, testing notes): support templates with more than two bodies — the wedge in a tusk tenon, the key in a wedged half-dovetail. The template reader is already N-role (per-body feature stacks); the pair assumption lives in engagement/assembly ("the mate-frame carrier is the mover"), which generalizes to one anchor + N movers, each with its own mate frame. The new concept is a **created-part role**: a body with no target timber in `body_map` — the tool clones it wholesale into the document (additive geometry is fine here; subtractive joinery governs cuts *into timbers*, and a wedge is a standalone stick), assembles it to the joint frame, and routes it to the Phase 2 hardware/peg schedule rather than the cut list.
- **Parametrically angled joints** (adopted July 2026, testing notes; sequence after per-joint handle and Save-as-template): joint angle as a VarSet property driving the landing-frame rotation, bounded by an angle range declared as template metadata (dialog clamps, linter enforces). Staged: **(a) vertical angles** — diagonal struts, rafter feet; one rotation in the timber's side plane — then **(b) plan angles** for out-of-square corners. The engagement/assembly layer is largely angle-blind by construction (sketches follow the landing frame rigidly; the MateFrame is a pure frame-coincidence declaration), so the work concentrates in the placement transforms (`FACES`, end semantics, mate parity, seating matrix all currently assume perpendicular), pre-flight bounds, footprint lint, and template authoring (cut profiles valid across the angle range). Angled cuts on *perpendicular* intersections (e.g. a diminished housing) need none of this — see Open Items.
- **Beam tool** (adopted July 2026, testing notes; staged): create an infill timber between two existing timbers — length from the two landing stations plus each end's tenon length (the subtractive `Length` convention makes this direct), joint template applied at both ends, auto-assembled. **It writes an expression, not a number** (see Parametric layout): binding `Length` to the grid rather than freezing a computed literal is what makes the infill track a later span edit, and it is most of that section's tooling work. **Stage 1: dialog infill beam** — select two timbers / landing stations in a dialog; perpendicular joints only; most of the payoff at a fraction of the cost. **Stage 2: the 3-click gesture** — click to place a landing frame on one timber, rubber-band line to a second landing frame, generate the timber at the line's length and angle (Assembly's joint-creation flow and Draft trackers are prior art). Stage 2 wants parametrically angled joints; until then the second click is constrained perpendicular per the template's metadata. Output is entirely native (a normal timber, two normal joints) — only the gesture is new.
- Subtractive convention assessed after Phase 0 assembly: runtime cost neutral (templates are cloned, not computed), template-design cost slightly higher (removal-region decomposition), bookkeeping decisively better (stick-length parameter, tape-measure-true drawing dimensions). Retained.

## Phase 2 — Cut Lists & Drawing Automation
- Cut list is a **procurement document** (per session-10 redesign): timber ID, species, grade, moisture, finish, cut type (boxed heart / FOHC / quartersawn), section, designed length, order length (= designed + trim-allowance parameter), board feet per stick, and order totals. Joinery callouts live on shop drawings / a joinery schedule, not the cut list.
- Specification fields (species, grade, moisture, finish, cut type) are Tier 2 properties on each timber; the generator reads them — the spreadsheet is output, never the source of truth.
- Hardware/peg schedule: generator sums per-joint counts (VarSet properties like PegCount) grouped by diameter; peg length derivable from bore depth + proud allowance.
- Batch TechDraw: projection-group-based dimensioned shop sheets per FabricationSignature (quantity + MemberID list on each; per-timber sheets as an option); frame/bent elevations. Generated sheets set dimension/font styles explicitly, never inheriting user preferences.
- **Positional IDs are display data** (settled at the Phase 1 shakedown, superseding the prior iteration's positional MemberID labels): the permanent identity is the serial Label (`T-Post-003`); position lives in `Position_Tag` (Tier 2, on the Dims VarSet) and is what drawings and cut lists print. Phase 2 may add structured Role/Bent/Position properties composing the tag; renumbering a position never touches a label, an expression, or geometry. Round-trips between model, drawings, and list. Because of that separation, labels themselves went **permissive** (July 2026, testing notes): free-form except the reserved characters `>`, `\`, `;`, and line breaks (strict lint — they break `<<Label>>` expressions or the Placement_Record; verified empirically against 1.1.1), ending in a separator (`-`/`.`/`_`/space) + digit serial that the copy tools bump, preserving the separator. See workflow doc §3.
- **FabricationSignature** (adopted): normalized hash of species, grade, section, stick length, end cut angles, and joint layout in timber-local coordinates. Identical signatures form fabrication groups in the cut list (`GROUP 7 — Qty: 4`). Handed mirrors hash differently (consistent with findings on handed pairs).
- Shop drawings carry reference-face marks and A/B end labels per the adopted face vocabulary (faces 1–4 clockwise from the reference face, viewed from end A).
- Evaluation item: per-bent driving **skeleton sketch** (native Sketcher) as the layout layer — the prior iteration's datum-line concept in native form.

## Phase 4 — Structural Checks (start simple, grow later)
1. **Load-path continuity** — every timber has a complete path to a bearing point; disconnected members flagged. Cheapest, most valuable early check.
2. Span-table checks (AWC tables via reference data system) and rule-of-thumb checks, advisory only.
3. Member stress checks: bending M ≤ Fb·S, shear V ≤ Fv·A·(2/3), deflection Δ ≤ L/360, driven by tributary-area load accumulation from **BuildingParameters** (roof material / snow / occupancy / wind presets, ASCE-derived, as a project-level parameter group).
4. FEM studies of individual joints (orthotropic properties via CalculiX) seeding a joint_capacities table (TFEC 1-2007 + FEA-derived).
5. Lightweight frame analysis with beam elements and semi-rigid joints from the capacities table; racking checks with per-bent brace contributions; bearing-point reaction schedule.
6. Load/capacity color overlay via native body ShapeColor (blue <30% → red >100%, grey unchecked); structural report with clickable findings.
Always labeled design guidance, not stamped engineering.

## Layout rules — Mill Rule primary; Square Rule / Line Rule as variants (reframed July 2026)

**The workbench's native convention is Mill Rule** (settled at the second-shakedown testing review, superseding the "Square rule" framing used through Phase 0). The drawings this design tool produces dimension an idealized straight, square timber — which is precisely a Mill Rule drawing. Square Rule's defining move — cutting the uneven surface of a rough-hewn stick down to the hypothetical ideal timber "inside" it — never appears on a drawing as a designed depth, because it depends on the unique variations of the specific log the framer selected for that position; it is field work with chalk line and spirit level, outside the model's scope. A framer working rough stock from our drawings does that reduction on site, finding the "milled" timber inside without planing the whole log. The housings we *do* draw are Mill Rule housings: **optional** bearing features that spread the load across the full beam width instead of relying on the tenon alone, with real designed depths — still supported and used, never required.

Earlier assessment (Phase 1, still accurate): the layout rule is **not** a foundation; it is a template-authoring convention riding on rule-neutral machinery. The rule is a *contract* between two templates — the timber template says where the reference planes are (section corner at the body origin → reference faces on the XZ/YZ origin planes), the joint template measures joinery from those planes — and the tools mostly clone whatever the author built rather than knowing geometry. The reference-face discipline is identical under Mill and Square Rule.

Corner-reference-baked pieces (shared by Mill and Square Rule), exhaustively:
1. `new_timber`'s section (reference corner at origin).
2. The `FACES` table + `_face_transform` in `apply_joint` — the only corner-reference-baked *tool code* (face complements `ddim - T`); ~20 isolated lines.
3. Two linter checks reference housing concepts (`joint-exceeds-footprint`, housing≤50% severing) — already no-op when a template has no `Housing_*` properties.
4. The `_Face1`/`_Face2` naming vocabulary.

Rule-agnostic (the bulk): the clone/rebuild machinery, `remove_joint`, junction-point coupling, end/hand placement transforms (frame-relative), the schema-driven dialog, and the **MateFrame** (a pure "these two frames coincide when engaged" declaration — zero knowledge of how either frame was derived; the reason engagement and future assembly are rule-blind by construction).

Cost:
- **Mill Rule = already built.** What exists today *is* Mill Rule: corner-referenced section, joint layout from reference faces and stick ends, housings as optional designed bearing features. No code owed.
- **Square Rule ≈ free.** Identical model geometry and drawings — the reduce-to-ideal housing is field work the framer performs on the rough stick, never a drawn dimension, so the model does not represent it. At most a label/note on drawings intended for rough stock.
- **Line Rule = moderate but contained.** Reference datum moves corner→center: a centered timber-template variant (centerline construction + half-widths; origin planes become centerplanes), a second `FACES` table (reflections about center, not corner complements, ~15 lines), and rule-aware linter vocabulary. Landing-frame expressions differ but are authored in the template, not tool code. No changes to clone/rebuild/mate/remove.

Structure when built: a single Tier 2 `Rule` property (`MillRule` default / `SquareRule` / `LineRule`) on timber Dims and joint templates; templates filter/label by it; New Timber offers the choice; `FACES` becomes rule-keyed; Apply Joint validates rule-compatibility; the linter branches face-vocabulary and housing checks on it. Caveat: a real Line Rule port wants an audit pass over every linter rule and the placement transforms to catch any corner-assumption under-counted above.

## Parametric layout — the grid drives, sticks derive (adopted July 2026)

**The problem.** Through the second shakedown, `Dims.Length` was authored and position was derived: type 12' for a tie and the solver puts the post wherever the joint frames land. That inverts the designer's intent. A tie with a 1" housing + 3" tenon at one end and a 1" housing + 11" through tenon at the other, set to 12'-0", yields 10'-8" clear inside — and a single `Span` value shared across bents with *different* joinery yields different actual dimensions bent to bent. Framers lay out on-center; the stick length is a consequence of the grid plus whatever joinery was chosen, never the other way round.

**The inversion.** The grid is authored; `Dims.Length` becomes an expression. No new object types, no new geometry — the project layer of the already-adopted layered parameter groups finally carrying real values.

- **Span basis is declared, not inferred.** A Tier 2 `Span_Basis` enum (`OnCenter` default / `ClearInside` / `BearingToBearing`) on the layout VarSet. **On-center is the native basis**: it is the only one stable under the edits actually made — changing a post section must change the clear span, not move the building.
- **Each joint publishes what it consumes.** `Stick_Allowance` = how much stick this joint adds *beyond the landing timber's grid line*, **measured along the entering timber's own axis** — `Tenon_Length + Housing_Depth - <landing ddim>/2`, where ddim is the landing timber's dimension along the joint normal (already tabulated: `FACES[n]["ddim"]`, Width on faces 2/4, Depth on 1/3). Negative means the stick stops short of the grid. Measuring along the member's own axis is what makes the arithmetic **angle-blind**, so diagonals need no separate mechanism.
- **The stick derives:** `Length = Bay_Span_OC + Stick_Allowance_A + Stick_Allowance_B`. Worked: 136" OC, 8" posts, 3"/11" tenons over 1" housings → allowances 0" and +8" → 144" stick, 128" (10'-8") clear. The clear dimension still varies between bents where posts or housings vary — correctly, and now visibly — while the **grid stays invariant by construction**, which is what the designer meant.

**The hard constraint: the layout VarSet must be a pure source.** The obvious arrangement — `Stick_Allowance` as a property *on the joint VarSet*, with the tie's `Length` summing the two — is impossible, and fails loudly (`cyclic reference to <doc>#JointVarSet001`). FreeCAD's dependency graph is **object-granular, not property-granular**, and every joint template already binds the joint to the entering timber's section (`Housing_Height = <<TDim_tie>>.Depth`, `Housing_Width = <<TDim_tie>>.Width`), so `jointVS → tieDims`; the moment `tieDims.Length` reads the joint back, the loop closes. No arrangement of properties on those two objects escapes it.

So the length arithmetic lives one level up, on a layout VarSet that **reads nothing that reads back from it**, and joints *consume* their tenon/housing from it rather than owning them. Corollaries: post sections are authored in the layout layer too (a layout VarSet that reads post Dims is also acyclic, but stops being acyclic the moment you want to drive those sections from it); the timber's `Length` expression must be written **last**, after both joints exist, since the second joint needs a resolved `Length` to place end B against. Nothing detects a cycle before FreeCAD refuses it — an advisory linter rule is owed.

**Verified** (headless shakedown, two posts + one tie, housed M&T both ends, plus the same chain hand-built in the GUI): stick derives to 144" from a 136" grid; `Bay_Span_OC` → 16'-0" moves the far post to 192.0000" solved on-center with the stick re-deriving to 200"; posts 8"→10" hold the grid at 192.0000" and re-cut the stick to 198" unaided; joints stay seated throughout (misfit ~1e-13 mm). In the GUI the bent updates on edit **with no explicit Solve** — editing the span touches the landing frames, which touches the Fixed joints, which pulls the assembly into the recompute. A manual solve is only needed after something moves *outside* the dependency graph, which is precisely what the Transform tool does.

**Diagonals — same mechanism, one level richer.** What changes is only the span term, and the insight is that **each diagonal family holds a different designer invariant, and it usually is not the span**:
- **Braces** — set out by run and rise on the two members, not by bay width. A 3'×3' brace stays 3'×3' when the bay widens; braces bind to `Brace_Run`/`Brace_Rise` and correctly ignore Span. Length `= sqrt(run² + rise²) + allowances`, angle `= atan2(rise, run)`.
- **Rafters** — the invariant is *pitch*: `Length = Run / cos(Pitch) + allowances`.
- **Struts** — an angle plus one anchored station.

The rule to build to: **the designer names the invariant; the template declares which one it holds; everything else derives.** Same shape as the `Handed` flag and the declared angle range — template self-describes, tools read it, no per-joint code. It lands directly on the adopted parametrically-angled-joints work, whose joint angle is already a VarSet property driving the landing frame, and `atan2` over layout values is a legal expression for it.

**Template authoring: the companion VarSet (verified July 2026).** `Stick_Allowance` *can* be authored in the joint template, via a second VarSet the template declares per joint — `Layout_J-<Kind>-<serial>`, kind-owner per the naming convention. It holds the length-consuming parameters (`Tenon_Length`, `Housing_Depth`) **authoritatively** plus the derived `Stick_Allowance`, and reads only the landing timber's Dims; the joint VarSet *consumes* tenon/housing from it. That direction is the whole trick — `tieDims.Length → companion → postDims` while `jointVS → companion` and `jointVS → tieDims`, so nothing the companion reads reads back. Verified end to end: stick 144" from a 136" grid, span→16' giving 200"/192.0000", posts 8→10" holding the grid at 192.0000", and — the edit that matters — changing the joint's tenon 11"→14" re-cutting the stick to 201" without moving the grid, joints seated throughout.

A second arrangement was tested and rejected: binding the junction *through* to the tie's section VarSet (so the joint never references the tie's Dims) also works, and lets the allowance live on the joint VarSet directly — but only when the section is group-bound. With a plain literal section, which is the default, there is nothing to bind through to and it is the same cycle. Not viable as the mechanism; not worth a second code path as an optimization.

Cost of the companion: `TemplateSpec` reads a second VarSet per joint; the generated Apply Joint dialog merges the two schemas (it is schema-driven, so a merge, not a rewrite); Duplicate and Remove Joint carry/clear the companion with its joint. Tree clutter is absorbed by the already-designed per-joint 3D handle, whose Group extension can hold both VarSets. Linter (strict): the companion must be a pure source — flag anything it reads that reads back — which is the rule that stops the cycle being rebuilt.

**Owed, in order.** (1) Build the companion-VarSet template support described above. (2) Apply Timber Joint / the Beam tool writing the timber's `Length` expression, opt-in per timber, with Remove Joint reverting the term to the resolved literal (mirroring how it already removes the Fixed assembly joint). (3) A derived `Clear_Inside` read-out per bay, so the dimension you do *not* drive stays visible, feeding a Phase 4 advisory check on bays diverging from typical. (4) Linter: expression-cycle advisory, and `Layout_`/project VarSet kinds in the naming rule (a hand-built `Layout_Main` currently trips `naming-convention`; `Project_Main` is already accepted).
