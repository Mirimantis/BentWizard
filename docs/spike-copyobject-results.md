## What the tests actually showed

- **The premise of round 2 holds.** The A-bis template — an
  `App::Part` holding a `JointParams` VarSet and the cutter Body as
  siblings — drives every sketch constraint and pad length by plain
  `<<JointParams>>.X`. There is no `href()` in it, so the
  dependency edges are real and the expression editor's
  autocomplete works the way it does everywhere else in FreeCAD.
  This is the shape round 1 had to abandon, because a Link exposes
  only the linked object's own properties.
- **Expressions remap.** This was the gate, and the thing Phase 0
  findings #2 and #12 were burned by. `copyObject(part, True)`
  rewrites the copy's expressions to name the copy's own VarSet:
  the second instance in one document references
  `<<JointParams001>>`, not `<<JointParams>>`. No expression in a
  copy names the source document or a source object, and no
  instance leaks a reference to a sibling instance. The full
  expression list is in the T1 table above rather than summarized,
  because that is the evidence.
- **Independence is total, in both directions.** Editing the copy
  moves only the copy; editing the source afterwards moves nothing
  downstream. That is a plain consequence of it being a copy, and
  it is the same practical position round 1 ended in — FEP-0010
  says a variant link cannot be refreshed from its template either.
  Round 2 simply does not pretend otherwise.
- **Boolean bridge:** `C1-Part` — PartDesign::Boolean referencing the copied App::Part.
  - `C1-Body` failed outright: `RuntimeError: Object can only be in a single GeoFeatureGroup`
  - `C2` constructs, producing a `PartDesign::Body`, but **ignores the instance placement** — parking the cutter clear of the stick left the cut in place.
  - `C3-Part` also passed, producing a `Part::Cut`.
  - `C3-Body` constructs, producing a `Part::Cut`, but does not follow a parameter change; **ignores the instance placement** — parking the cutter clear of the stick left the cut in place; logs a scope violation: `Part::Cut: Link(s) to object(s) 'Cutter' go out of the allowed scope 'JointCut'. Instead, the linked object(s) reside within 'JointTemplate'.`.

  The structural point: the operand is a copied `App::Part`
  containing a Body, and **the Part is what the Boolean must
  take**. Handing it the Body *inside* the Part raises `Object
  can only be in a single GeoFeatureGroup` — the Body already
  belongs to the Part. `Part::Cut` will accept the inner Body
  and even produce the right solid, but logs a scope violation
  while doing it; that is a trap worth naming, because the
  volume looks right.

  The placement check matters as much as the volume: parking
  the instance clear of the stick returns the timber whole, so
  the Part's `Placement` really is what positions the joint.
  That is the hook an apply-joint tool would drive.

- **No `hasher mismatch` warnings.** Round 1 emitted them
  continuously from its boolean recomputes; round 2's T6 run is
  clean. Given this project's history with topological naming —
  and that stable element names are what keep a TechDraw
  dimension attached to the edge a framer picked — that is a
  meaningful difference, not cosmetics.

- **`copyObject` is the slower and heavier of the two.**
  At 150 instances it builds in 44.0 s against round 1's
  12.2 s, full-recomputes in 8.3 s against 2.8 s, and
  carries 36 objects per timber-plus-joint against 29.
  A deep copy duplicates the cutter's whole feature tree,
  including a second `App::Origin`, where a variant link's
  materialized copy is leaner. File size is near-identical
  (3.2 MB against 3.1 MB), so this is object count and
  recompute work, not storage. Both are comfortably inside
  what a frame needs; neither degrades non-linearly.

## Recommendation

**Adopt `copyObject`.**

Both mechanisms produce an independent, fully parametric joint
instance with the correct solid, and both scale acceptably. The
difference is entirely in what they cost to author and to live
with, and on that the comparison table above is one-sided:
`copyObject` needs no `href()`, no property status that only
Python can set, and sits in front of none of round 1's four
open upstream issues. It also leaves a delivered file with no
external reference at all, where a variant link leaves a
dangling template path that FreeCAD complains about on open.

The price is performance, and it should be stated plainly:
`copyObject` is roughly two to three times slower to build and
recompute at frame scale, and carries about a quarter more
objects per joint. That buys nothing — it is simply what a deep
copy costs. It is worth paying because the numbers are still
well inside usable (see the scale table), and because the
authoring cost it removes is paid by every user on every
template, forever, while the recompute cost is paid by a
machine.

The one thing a link could have bought — a live connection to
the template — is exactly what FEP-0010 says cannot be used.
Paying link ergonomics for a connection that must not be
exercised is not a trade worth making.

Critically for this project's own requirement: a template
author under round 2 builds an `App::Part`, a VarSet and a Body
with sketches, all in the GUI. No Python console. That is the
"no programming to add a joint" requirement met, and round 1
cannot meet it.

### What instancing still does not do

`copyObject` replaces the *geometry-cloning* part of
`apply_joint.py` and nothing else. Still owed by the tool:

1. **Mated pairs.** A joint is two halves. Instancing clones one
   cutter; the workbench's one-VarSet-per-joint contract, which
   parameterizes both halves together, has to be built on top —
   a shared joint VarSet the two instances' parameters bind to.
2. **Mate frames and the stick-allowance contract.** The mate
   frame's offset from the stick end *is*
   `Stick_Allowance_FTF`, and it is what makes driven `Length`
   work. A copied Part carries no frame role and no allowance;
   the frames-at-face convention and `Frame_Role` are the
   tool's, not the mechanism's.
3. **Placement.** T3 shows the Part's `Placement` positions the
   cut, but computing it — end A/B, faces 1–4, hand, the
   mirrored-sketch angle negation and the frame-child offset
   axis rule that round 1's sibling bugs exposed — is the
   spatial work, and it is untouched by either mechanism.
4. **Naming and filing.** `Joint_MT001`/`JointParams001` is
   FreeCAD's uniquifier, not the convention. Relabelling to
   `J-<Kind>-<serial>` and the `.<Abbrev>.<serial>` feature
   suffixes, creating the handle, filing it in the bent's
   `TimberJoints_<Assembly>` group — all still the tool's job.
5. **Assembly seating.** Auto-assembly, the Fixed joint, the
   mate-parity rule for faces 1–3. Untouched.

So this is a decision about *how a template becomes an
instance*, not a licence to delete the rebuild engine. The
honest framing: `copyObject` could replace the clone-and-remap
core of `apply_joint.py` with a one-line API call and a
deterministic relabel pass, and the surrounding placement,
naming and assembly logic stays exactly as it is.

  demonstrated. Build `scratch/r2_template.FCStd`'s equivalent by

  one tidy node with the VarSet and Body under it, and whether the
  duplicated Origins are visible clutter.
- **Assembly.** Out of scope headless: whether a timber cut by a
  copied Part behaves as an ordinary component.
- **TechDraw correctness.** T6 proves no exception, not a correct
  drawing.
- **The artifacts above** are saved for exactly this.
