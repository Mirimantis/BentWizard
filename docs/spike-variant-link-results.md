## What won

- **`LinkCopyOnChange` mode.** All three of `Enabled`, `Owned` and
  `Tracking` materialize a copy and hold the override; the remaining
  tests ran on `Enabled`. The difference the harness can see is *when*
  the copy appears: `Owned` creates its `LinkCopyOnChangeGroup`
  immediately, `Enabled` and `Tracking` create it lazily, on the
  first override.
- **Boolean bridge:** `C2` — SubShapeBinder + PartDesign::Boolean.
  - `C1` also worked, producing a `PartDesign::Body`.
  - `C3` also worked, producing a `Part::Cut`.

  `C2` is reported as the winner because the brief asks for it
  first and it is the documented PartDesign route, but `C1` is
  the better answer on the evidence: contrary to the brief's
  expectation, `PartDesign::Boolean` accepts an `App::Link`
  directly in its `Group`, giving the same Body, the same exact
  volume and the same editability with one fewer object per
  joint. `C3` is correct too but turns the timber into a
  `Part::Cut`, which is the object-type change that would
  ripple through every downstream consumer.

  One authoring trap in `C2`: a `SubShapeBinder` created
  *inside* the Body is already claimed by it, and handing it to
  the Boolean raises `Object can only be in a single
  GeoFeatureGroup`. The binder has to be created at document
  level and let the Boolean adopt it.

## Why the manual GUI session saw no copy

Two preconditions, neither visible in the property editor:

1. **The source property must carry the `CopyOnChange` property
   status.** The negative control in T1 — the same cutter with the
   status omitted — exposes *no* dynamic properties on the Link at
   all, which is exactly the symptom the manual session recorded.
   The status is set with
   `obj.setPropertyStatus(name, 'CopyOnChange')`; the Add-property
   dialog offers no way to set it, so a hand-authored template needs
   the Python console or a macro for this one step.
2. **The source document must be saved.** Creating a
   cross-document `App::Link` against an unsaved document raises
   `Linked document not saved` outright.

The override must also be written to the Link's own dynamic
property, not into the linked object. The harness only ever assigns
`link.<Param>`, and asserts the source value unchanged afterwards.

## Notes on the individual tests

- **T1.** After an override `link.getLinkedObject(True)` resolves
  into the *target* document: the copy is real and local, and the
  source keeps its authored value.
- **T2.** Binding a Link's dynamic property to
  `<<Group_Test>>.MortiseThickness` works, survives save/reload, and
  drives every instance bound to it, so the layered
  parameter-group architecture is not blocked by this mechanism.
  Two behaviours carry forward: the copy materializes on the first
  *change* of the expression's value rather than when the expression
  is set, and clearing the expression for a per-instance literal
  leaves siblings alone — the override semantics the workbench
  already documents.
- **T3.** Volumes are compared against an analytic expectation
  (timber minus cutter), never against each other, so a bridge that
  silently removes nothing is caught rather than passed.
- **T4.** Note what relocation really tests here. Once the copy has
  materialized the geometry lives *inside* the target document, so
  the target survives its source file being deleted. That is a
  genuine deployment advantage over a library of external
  templates — and the flip side of FEP-0010's warning that a
  copy-on-change link cannot be refreshed from its template without
  converting to a regular link and discarding per-instance
  parameters.
  The two relocation cases separate cleanly. Moving the target
  *alone* leaves the source unreachable — FreeCAD looks for it
  beside the target, not at the absolute path it was linked from,
  logs `does not exist!`, and carries on — and the geometry is
  still right, because the copy is local. Moving both together
  resolves the source by relative path and opens it. So a joint
  library is a *build-time* dependency under this mechanism, not a
  runtime one: a delivered model does not need the library beside
  it, but it also cannot be refreshed from it.
- **T5.** At 150 instances: 2.8 s full recompute, 4.48 s for
  a one-value parameter change, 3.1 MB on disk, 4351 objects
  in the document.
- **Console noise.** Boolean recomputes emit repeated
  `TopoShapeExpansion.cpp: hasher mismatch` warnings throughout the
  run. Nothing failed and every volume is exact, but it is
  element-mapping (topological naming) machinery complaining, and
  it is worth watching if this mechanism is adopted — stable
  element names are what keep a TechDraw dimension attached to the
  edge a framer picked.
- **T6.** Headless TechDraw is a smoke test: it proves the page,
  projection and dimension recompute without raising after a link
  parameter changes. It says nothing about whether the dimension
  still points at the edge a framer meant.

## Recommendation

**Go on the mechanism — but see the four costs below before
treating it as a replacement for `apply_joint.py`.**

Against the brief's criteria this is a go: T1 and T2 pass,
the `C2` bridge preserves both the cut and the timber's
native editability while leaving the top-level object a
`PartDesign::Body`, T4 passes, and T5 is workable at 150
instances. Nothing downstream has to change to accommodate
the object type: the timber is still a Body whose `Tip` is a
`PartDesign::Boolean`, so the linter, the cut-list walker,
the TechDraw batch and the assembly code all keep addressing
a Body.

### What a go would cost, and what it does not buy

1. **Parameters must live on the linked object itself.** A Link
   exposes only the linked object's own properties, so a
   cutter's parameters sit on the Body and drive its sketches
   through `href()` — which severs the dependency edge and
   disables expression autocomplete. That is the shape of every
   template under this mechanism, and it is a step down in
   authoring ergonomics from the VarSet the workbench uses now.
2. **`href()` is a documented weak point.** Upstream #24715 is
   an open report of a copy-on-change variant not updating with
   changed custom properties, in a configuration close to this
   one. The harness does not reproduce it headlessly; that is
   not evidence it is fixed.
3. **Template revision does not propagate.** Per FEP-0010, and
   consistent with T4's self-containment, revising a library
   template cannot be pushed into existing instances without
   converting them to regular links, which discards their
   per-instance parameters. The rebuild engine can re-apply a
   revised template; this mechanism cannot.
4. **A cutter is half a joint.** The spike cuts one negative
   into one timber. BentWizard's joint VarSet parameterizes both
   halves at once, and the mate frame / `Stick_Allowance_FTF`
   contract is what makes driven `Length` work. A link-based
   mechanism needs a second cutter, a mate frame the link does
   not carry, and a way to keep both instances' parameters in
   step — in practice a shared VarSet per joint plus placement
   logic, which is most of what `apply_joint.py` already does.
   The spike retires the *question*; it does not by itself
   justify the rewrite.

## Needs GUI confirmation before acting

- **Recompute triggers.** Headless recompute is not the GUI's. The
  tables above record every place a *forced* recompute
  (`doc.recompute(None, True, True)`) was needed to see a change;
  in the GUI those are the cases most likely to show a stale view or
  a touched object that never clears.
- **The property editor.** Whether the Link's exposed `Joint` group
  is editable in the property panel, and how a trailing digit
  renders (`Setback Face 1` vs `Setback Face1`) — the naming
  question the manual session raised.
- **Assembly.** Out of scope headless. Whether a cut timber behaves
  as an ordinary component, and whether 150 materialized copies
  confuse the solver, has to be seen in the GUI.
- **TechDraw correctness.** T6 proves no exception, not a correct
  drawing. Whether dimensions stay attached to the edges a framer
  picked needs eyes on a page.
- **Upstream #13481, #30124, #19182.** The harness does not
  reproduce these headlessly; all three are GUI-workflow shaped
  (links Owned inside an `App::Part`, switching a binder to
  Detached, switching configurations). Retest in the GUI before
  relying on the mechanism.
